# プロダクト要件定義書（PRD）: ObsidianConscierge

## プロジェクト概要

**プロジェクト名:** ObsidianConscierge
**バージョン:** 1.0 (Initial Release)
**最終更新日:** 2025-12-12

ObsidianConsciergeは、Obsidianでのノート管理と知識の再発見に特化した、自動化・AI駆動型のソリューションです。3つの主要なサービス（Core Indexing, Daily Insight, Analysis）から構成され、ユーザーが「書くこと」と「考えること」に集中できる環境を提供します。

### 既存実装との関係

本プロジェクトは、`sample_code/` フォルダに存在する**実証済みの実装を基盤**として構築します。

**既存実装の主要機能**:
- TF-IDF分析システム（5,800+ファイルの自動タグ付け、45種類の例外パターン）
- ChromaDB統合（ベクトル検索、sentence-transformers使用）
- MOC（Map of Contents）生成
- デイリーノート自動生成
- 類似度分析・リンク挿入
- 階層型クラスタリング（Jupyter Notebook実装）

**新システムでの主要な変更点**:
- LLM（テキスト生成）: ChatGPT API → **Ollama（ローカル、llama3/mistral）**
- Embedding: **sentence-transformers（既存実装を継続使用）** - 高速で実績あり
- パッケージ管理: Poetry想定 → **uv（高速パッケージマネージャー）**
- UI: なし → **FastAPI + TypeScript（軽量、基本機能のみ）**
- Git同期: 手動 → **自動化スクリプト（TargetObsidianVaultディレクトリ）**

## A. Core Service: Vector Indexing & DB Management

システムの中核となる基盤機能です。GitHubリポジトリから記事を取得し、ベクトル化してデータベースに格納します。

### A-1: Git変更検知

| 項目 | 詳細 |
|------|------|
| **機能名** | Git変更検知 |
| **概要** | GitHubリポジトリの変更を定期的に検知し、差分ファイルを特定する |
| **実装要件** | - 最後に処理したコミットIDを保存（`data/last_commit.txt`またはDB）<br>- 次回の実行時に`git log`またはGitHub APIで比較<br>- 新規/更新/削除された`.md`ファイルをリスト化<br>- 変更タイプ（added/modified/deleted）を分類 |
| **入力** | - GitHubリポジトリURL<br>- GitHubトークン<br>- 前回処理済みコミットID |
| **出力** | - 変更ファイルリスト（パス、変更タイプ、コミットID） |
| **エラーハンドリング** | - ネットワークエラー時のリトライ（最大3回）<br>- 認証エラー時の明確なエラーメッセージ |

### A-2: コンテンツ抽出

| 項目 | 詳細 |
|------|------|
| **機能名** | コンテンツ抽出 |
| **概要** | マークダウンファイルから、本文、タイトル、メタデータ（YAML Frontmatter）を抽出する |
| **実装要件** | - YAML Frontmatterをパースしてメタデータとして保存<br>- コードブロック（```...```）は除外または別途処理<br>- 画像リンク、URL、HTMLタグのクリーニング<br>- 見出し（#）からタイトルを抽出（Frontmatterにtitleがない場合）<br>- 空行や不要な装飾マークダウンをクリーニング |
| **入力** | - マークダウンファイルのパス<br>- ファイル内容（文字列） |
| **出力** | - タイトル（文字列）<br>- 本文（クリーニング済み文字列）<br>- メタデータ（辞書型：tags, created, modified, etc.） |
| **依存ライブラリ** | `frontmatter`, `markdown` |

### A-3: ベクトル生成

| 項目 | 詳細 |
|------|------|
| **機能名** | ベクトル生成 |
| **概要** | 記事の本文とサマリー（要約文）をベクトル（埋め込み）に変換する |
| **実装要件** | - **本文ベクトル**：記事全体の内容を数値化（768次元）<br>- **サマリーベクトル**：後述のサマリーを数値化<br>- 使用モデル：**sentence-transformers/distiluse-base-multilingual-cased-v2（既存実装を継続）**<br>- 長文の場合はチャンク分割（最大512トークン）<br>- **既存実装**: `find_similar_documents.py`のembedding関数をそのまま活用 |
| **入力** | - 本文テキスト<br>- サマリーテキスト |
| **出力** | - 本文ベクトル（numpy配列またはリスト、768次元）<br>- サマリーベクトル（numpy配列またはリスト、768次元） |
| **パフォーマンス要件** | - 1記事あたりの処理時間：1秒以内（高速、実績あり） |
| **実装状況** | **既存実装を継続使用**（sentence-transformers、実証済み） |

### A-4: サマリー自動生成

| 項目 | 詳細 |
|------|------|
| **機能名** | サマリー自動生成 |
| **概要** | 新規・更新記事に対し、内容に基づいた要約文をAIで自動生成する |
| **実装要件** | - LLM（**Ollama: llama3/mistral**）を使用<br>- 記事の長さに応じて適切な長さ（200字程度）のサマリーを生成<br>- プロンプトテンプレート：<br>  "以下の記事を200字程度で要約してください。重要なキーワードや概念を含めてください。\n\n{article_content}"<br>- **既存実装**: `makesummary_using_chatgtp.ipynb`をOllama SDKに移植 |
| **入力** | - 記事本文 |
| **出力** | - サマリーテキスト（文字列、200字程度） |
| **エラーハンドリング** | - Ollama接続エラー時のリトライ（最大3回）<br>- タイムアウト処理（60秒）<br>- フォールバック：Ollamaが利用不可の場合は、サマリーなしで処理継続 |
| **実装状況** | **既存実装を改修**（ChatGPT API → Ollama SDK） |

### A-5: タグ自動提案/生成

| 項目 | 詳細 |
|------|------|
| **機能名** | タグ自動提案/生成 |
| **概要** | 記事の内容から適切なタグをAIで自動提案・生成し、既存の手動タグと統合する |
| **実装要件** | - 既存タグ（Frontmatterから抽出）との重複チェック<br>- 過度に一般的なタグ（例：「メモ」「日記」）の生成を防ぐ<br>- タグ数は3〜7個を目安<br>- プロンプトテンプレート：<br>  "以下の記事の内容に基づいて、3〜7個の適切なタグを提案してください。既存のタグは{existing_tags}です。\n\n{article_content}"<br>- 生成されたタグを既存タグとマージ |
| **入力** | - 記事本文<br>- 既存タグ（リスト） |
| **出力** | - 統合タグリスト（リスト） |
| **設定** | - タグ自動生成のON/OFF（設定ファイルで制御可能） |

### A-6: ベクトルDB格納

| 項目 | 詳細 |
|------|------|
| **機能名** | ベクトルDB格納 |
| **概要** | 記事ID（ファイルパス）、本文ベクトル、サマリーベクトル、サマリーテキスト、タグ、更新日時をDBに保存 |
| **実装要件** | - **ベクトルDB:** ChromaDB（推奨）<br>- コレクション名：`articles`<br>- データ構造：<br>  - `id`: ファイルパス（相対パス）<br>  - `embedding`: 本文ベクトル<br>  - `summary_embedding`: サマリーベクトル<br>  - `metadata`: {title, summary, tags, created, modified, file_path}<br>- 既存レコードの更新処理（IDが同じ場合は上書き） |
| **入力** | - 記事ID、ベクトル、メタデータ |
| **出力** | - 格納成功/失敗のステータス |
| **パフォーマンス要件** | - バッチ処理対応（100件ずつ） |

### A-7: データ削除処理

| 項目 | 詳細 |
|------|------|
| **機能名** | データ削除処理 |
| **概要** | Gitで削除されたファイルに紐づくDBレコード（ベクトル、メタデータ）を削除する |
| **実装要件** | - 削除されたファイルパスを特定<br>- ChromaDBから該当IDのレコードを削除<br>- 削除ログを記録 |
| **入力** | - 削除されたファイルパスのリスト |
| **出力** | - 削除成功/失敗のステータス |

### A-8: CUI検索

| 項目 | 詳細 |
|------|------|
| **機能名** | CUI検索 |
| **概要** | デバッグ・初期検証用に、コマンドラインからセマンティック検索を実行できる機能 |
| **実装要件** | - 検索クエリを入力<br>- 最も類似度の高いK件の結果を表示（デフォルト：5件）<br>- 表示項目：タイトル、サマリー、類似度スコア、ファイルパス<br>- インタラクティブモード：`poetry run python scripts/search_cli.py` |
| **入力** | - 検索クエリ（文字列）<br>- 結果数（K、オプション） |
| **出力** | - 検索結果リスト（タイトル、サマリー、類似度、パス） |

## B. Daily Service: Insight Report & Search UI

ユーザーが日常的に利用するインターフェースおよびルーティン支援機能です。

### B-1: カスタム検索UI

| 項目 | 詳細 |
|------|------|
| **機能名** | カスタム検索UI |
| **概要** | ベクトルDBを叩くためのシンプルなWebインターフェース |
| **必須要件** | 1. **セマンティック検索**（自然文入力）<br>2. **フィルタリング**（タグ、更新日時）<br>3. 検索結果表示（タイトル、サマリー、類似度）<br>4. ページネーション（20件/ページ） |
| **UI要件** | - レスポンシブデザイン（モバイル対応）<br>- リアルタイム検索（入力中に検索実行、デバウンス300ms）<br>- 検索結果のハイライト表示<br>- Obsidianで開くボタン（各結果に配置） |
| **API仕様** | - `GET /api/search?q={query}&tags={tag1,tag2}&limit={limit}&offset={offset}`<br>- レスポンス：`{results: [...], total: number, page: number}` |
| **技術スタック** | FastAPI + HTML/JavaScript（Vanilla JSまたはVue.js） |

### B-2: デイリーレポート生成

| 項目 | 詳細 |
|------|------|
| **機能名** | デイリーレポート生成 |
| **概要** | 毎朝の運用を支援するためのレポートを生成する（MarkdownまたはHTML形式） |
| **コンテンツ** | 1. **昨日の執筆統計**<br>   - 新規記事数<br>   - 更新記事数<br>   - 総文字数<br>   - 執筆時間（推定）<br>2. **重複検知警告**（類似度80%以上）<br>   - 重複記事ペアのリスト<br>   - 類似度スコア<br>3. **ランダムピックアップ3記事**（異分野優先）<br>   - 異なるタグを持つ記事を優先的に選択<br>   - タイトル、サマリー、最終更新日<br>4. **MOC候補リスト**（後述） |
| **出力形式** | - Markdown（`reports/daily/{YYYY-MM-DD}.md`）<br> - HTML（`reports/daily/{YYYY-MM-DD}.html`）<br> - Web UIでも表示可能 |
| **実行タイミング** | - 毎日午前6時（cron/systemd）<br> - 手動実行も可能 |

### B-3: MOC候補リスト

| 項目 | 詳細 |
|------|------|
| **機能名** | MOC候補リスト |
| **概要** | タグが多いが、既存のMOC（目次ページ）にまだリンクされていない記事を抽出する |
| **実装要件** | - MOCページの定義：`MOC.md`または`index.md`を含むファイル、または特定のタグ（例：`#MOC`）を持つファイル<br>- MOCページ内のリンク（`[[article]]`形式）を抽出<br>- リンクされていない記事を抽出<br>- 優先度：タグ数が多い順、更新日が新しい順 |
| **入力** | - 全記事リスト<br> - MOCページリスト |
| **出力** | - MOC候補記事リスト（タイトル、パス、タグ数、優先度） |

### B-4: 記事への連携

| 項目 | 詳細 |
|------|------|
| **機能名** | 記事への連携 |
| **概要** | 検索結果やレポートの項目をクリックすると、ローカルのObsidianアプリケーションで該当記事を開けるようにする |
| **実装要件** | - `obsidian://open?vault={vault_name}&file={file_path}`形式のURIを生成<br>- ファイルパスはURLエンコード<br>- ブラウザでクリック時にObsidianアプリが起動<br>- フォールバック：ファイルパスをクリップボードにコピー |
| **設定** | - Vault名は`.env`で設定 |

## C. Analysis Service: Knowledge Map & Strategic Insight

知識の構造を分析し、クリエイティブなインサイトを提供する機能です。日次または週次で実行されます。

### C-1: 重複検知と報告

| 項目 | 詳細 |
|------|------|
| **機能名** | 重複検知と報告 |
| **概要** | 全記事間のベクトル距離を計算し、閾値（例: 80%）を超えた記事ペアを「重複候補」として報告する |
| **実装要件** | - 全記事のベクトルペア間のコサイン類似度を計算<br>- 閾値：80%（設定可能）<br>- 重複記事のタイトル、サマリー、類似度をデイリーレポートに含める<br>- パフォーマンス最適化：全ペア計算は重いため、サマリーベクトルを使用して高速化<br>- 週次で全ペア計算、日次で新規記事とのみ比較 |
| **入力** | - 全記事のベクトル |
| **出力** | - 重複候補リスト（記事ペア、類似度） |
| **計算量** | - O(n²) → 最適化後：O(n×m)（n: 全記事数、m: 新規記事数） |

### C-2: 記事のクラスタリング

| 項目 | 詳細 |
|------|------|
| **機能名** | 記事のクラスタリング |
| **概要** | 全記事のベクトルに基づき、意味的に近い記事群（クラスター）を特定する |
| **実装要件** | - アルゴリズム：K-meansまたは階層的クラスタリング（scikit-learn）<br>- クラスター数（K）は自動決定（エルボー法）または手動設定<br>- 各記事にクラスターIDを付与<br>- クラスターの代表記事（中心に最も近い記事）を特定 |
| **入力** | - 全記事のベクトル |
| **出力** | - クラスターID（各記事に付与）<br> - クラスター情報（ID、代表記事、記事数） |
| **実行頻度** | - 週次（全記事数が100件以上の場合） |

### C-3: ブリッジ記事の特定

| 項目 | 詳細 |
|------|------|
| **機能名** | ブリッジ記事の特定 |
| **概要** | 複数の異なるクラスターの中心に最も近く位置する記事を「ブリッジ記事」として特定する |
| **実装要件** | - 各記事について、複数のクラスター中心への距離を計算<br>- 複数のクラスター（3つ以上）と平均的に近い記事を特定<br>- 特定したブリッジ記事をレポート化<br>- なぜブリッジとなり得るのかを分析（複数のタグを持つ、異なるクラスターと平均的に近いなど） |
| **入力** | - クラスタリング結果<br> - 全記事のベクトル |
| **出力** | - ブリッジ記事リスト（記事ID、関連クラスター、分析結果） |

### C-4: ナレッジマップデータ生成

| 項目 | 詳細 |
|------|------|
| **機能名** | ナレッジマップデータ生成 |
| **概要** | クラスタリング結果（ノードとクラスタID）をJSON形式で出力し、可視化UIのデータソースとする |
| **実装要件** | - **ノードデータ**：記事ID、クラスターID、x/y座標（t-SNEまたはUMAPで次元削減）<br>- **ブリッジ記事フラグ**を含める<br>- JSON形式：`{nodes: [...], clusters: [...], bridges: [...]}`<br>- ファイル出力：`data/knowledge_map.json` |
| **入力** | - クラスタリング結果<br> - 全記事のベクトル |
| **出力** | - JSONファイル（ナレッジマップデータ） |
| **依存ライブラリ** | `umap-learn`または`sklearn.manifold.TSNE` |

### C-5: 可視化UI (Knowledge Map)

| 項目 | 詳細 |
|------|------|
| **機能名** | 可視化UI (Knowledge Map) |
| **概要** | クラスタリング結果を視覚的に表示するWebインターフェース |
| **要件** | - 記事をノードとして描画（D3.jsまたはvis.js）<br>- クラスターごとに色分け<br>- ホバーで記事タイトルを表示<br>- クリックで記事詳細を表示<br>- ブリッジ記事を強調表示（太線、異なる色）<br>- ズーム・パン機能 |
| **技術スタック** | D3.jsまたはvis.js + FastAPI |
| **API仕様** | - `GET /api/knowledge-map` → JSONデータを返す |

### C-6: 統合提案と構成案

| 項目 | 詳細 |
|------|------|
| **機能名** | 統合提案と構成案 |
| **概要** | 重複候補またはベクトル的に近い3〜5記事を検出し、LLMで統合後のタイトルとアウトライン（構成案）を提案する |
| **実装要件** | - 重複候補または類似記事グループを特定<br>- LLMに以下のプロンプトを送信：<br>  "以下の複数の記事を統合して、1つの包括的な記事にまとめることを検討しています。統合後のタイトルと、詳細なアウトライン（見出し構造）を提案してください。\n\n記事1: {title1}\n{summary1}\n\n記事2: {title2}\n{summary2}\n\n..."<br>- 週次レポートに含める |
| **入力** | - 類似記事グループ（3〜5記事） |
| **出力** | - 統合提案（タイトル、アウトライン） |

## D. 技術スタック

| 項目 | 採用技術 | 理由 |
|------|---------|------|
| **メイン言語** | Python 3.11 | LLM/ベクトル処理ライブラリが豊富で、自動化スクリプトの実行が容易。既存実装との互換性。 |
| **パッケージ管理** | **uv** | 高速で現代的なPythonパッケージマネージャー。Poetryより高速で依存関係解決が優れている。 |
| **ベクトルDB** | ChromaDB | ローカルでの実行が可能で、スケーラビリティと柔軟なメタデータ検索に対応。既存実装で実績あり。 |
| **LLM** | **Ollama（llama3/mistral）** | ローカル実行可能でプライバシー保護。APIコスト不要。GPT-4/Claudeと同等の性能。 |
| **Embedding** | **sentence-transformers（distiluse-base-multilingual-cased-v2）** | 多言語対応で高品質。既存実装で実績あり。高速で安定。ChromaDBと統合済み。 |
| **Webフレームワーク** | FastAPI | 高速で現代的なPython Webフレームワーク。型ヒント対応、自動ドキュメント生成。 |
| **フロントエンド** | **TypeScript + HTML/CSS** | 軽量でシンプル。基本的な対応のみ。型安全性を確保。 |
| **可視化** | D3.js または vis.js | インタラクティブなナレッジマップの実装（Phase 3）。 |
| **TF-IDF分析** | **scikit-learn + janome** | 既存実装で実績あり。日本語形態素解析に対応。 |
| **Git操作** | **GitPython** | Python内でGit操作を実行。TargetObsidianVaultの自動同期に使用。 |
| **自動化実行** | Pythonスクリプト + `cron` / `systemd` | シンプルでOSに依存しない自動実行システム。 |
| **テスト** | **pytest + pytest-cov** | 念入りにテストを実施。カバレッジ測定。80%以上を目標。 |
| **Linter/Formatter** | **ruff** | 高速で現代的なPython Linter/Formatter。flake8/black/isortの代替。 |
| **型チェック** | mypy | 静的型チェックによる品質向上。すべての関数に型ヒントを付与。 |
| **データ検証** | pydantic | FastAPIと統合。動的な型付けに対してエラーを明示的に発生。 |
